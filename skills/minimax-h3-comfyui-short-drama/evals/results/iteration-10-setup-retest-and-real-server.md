# 迭代 10：装机与规划第二次复测 + 真实 ComfyUI 0.37.2 验证（2026-11-23）

两件事。先是第二次请一个没有上下文的 agent 按用户的真实条件（Windows 11、RTX 4090 24 GB、ComfyUI 0.37.2 便携版、只能从 HuggingFace / GitHub 下载、手里没有任何素材）走一遍「装机 → 出图规划 → 30 s 分镜 → 提交草稿 → QC → 装配」；再是修它的发现时，第一次在容器里装起了一台**真实的 ComfyUI 0.37.2**（仅 CPU，模型文件用空的占位文件），用它自己的节点定义、前端导出和校验器来核对 skill。

## 复测结论：「部分可以」（上一轮是「不行」）

分镜 → 提示词 → 提交 → QC → 装配这条链是确定的，在替身素材上第一次就走通；出图和首帧、音色锚点、精修、几处装机细节仍然要猜，另有一处文档和工具对不上可能拦住每一条 take。

| 发现 | 性质 | 处理 |
|------|------|------|
| 种子接在 Primitive 节点上时，`--batch` 拒绝；单条提交被记成「seed 0」，下一个 seed 落进同一个目录 | 脚本缺陷 | 原始值节点上的种子可以设；由别的节点算出来的种子明确拒绝并说明怎么改 |
| 连不上服务器的 `--dry-run` 跳过预检却不说 | 脚本缺陷 | 不需要服务器的那几项（帧格、宽高、参考键名、标签）照做，并写明哪些没查 |
| 文档说预览会查、其实没查：引导器接在 shift 节点之前、Ref2VA 用了 shift 6、LoRA 和底模不是一家、两个蒸馏 LoRA 叠在一条链上、Sage 和 LowVRAM 同开、bf16 底模、30 fps | 文档与工具不符 | 都补进 advice |
| 出图工作流上打印 H3 的 advice（CFG 4 被劝成 1） | 脚本缺陷 | 没有 H3 节点的工作流不出 H3 的建议 |
| 给缺失的 Ref2V LoRA 推荐了一个 FL2V 文件 | 脚本缺陷 | 「最接近的文件」只在同一家里找 |
| 每次预览都提醒 16:9 的图放在 7:4 画布上差 1.6% | 噪声 | 阈值提到 3% |
| 精修预览不显示二采、估时用的是草稿的耗时 | 脚本缺陷 | 预览显示二采的尺寸和强度；估时只用同一个工作流的历史 |
| 加了音色之后一次普通的重建会改写已采纳段的提示词，同 seed 精修出来不再是那条片段，而且没有任何提示 | 确认的陷阱 | `build_prompts.py` 保留已采纳段的提示词（`--only` 才重建）；精修预览比对提示词和参考的指纹，一致就写明、不一致就警告 |
| `extract_tail_frame.py --trim-freeze` 留下的 `_trimmed.mp4` 被 QC 当成一条 take，报时长不符 | 脚本缺陷 | QC 对同一条 take 只看一次（被取代的旧 take、裁过的副本在原片也在列表里时跳过；单独点名的文件照常看） |
| 拼错的字段名被静默忽略；自由否定句只在 lint 里警告 | 脚本缺陷 | 校验器对未知字段给警告并提示最接近的名字，对否定句给警告；铁律 2 写明看到警告要改 |
| `MiniMaxH3AddGuide` 的输入在表里写成全是必填 | 文档错误 | 按真实定义标出可选项 |
| 出图阶段没有可用的工作流、没有逐张图的命令、首帧模板没有道具的写法 | 文档缺失 | 附带出图工作流；`image-stage.md` §4 加逐类图的命令表；`image-prompts.md` §6 加道具句、两步编辑、过肩镜头的规则 |
| 13 处互相矛盾或不对的说法（「求快用 544p 档」对「Ref2V 没有 8 步 544p LoRA」、11 / 11 / 10 s 对「段压到 ≤ 10 s」、「≥ 6 s 样本」对「每句 ≤ 20 字」、两个不同的耗时外推、禁词里有 `cinematic` 而示例里也有，等） | 文档矛盾 | 逐条改掉；耗时写成 5–10 min 并说明两种外推的来历；第一次做用四段 9 / 9 / 8 / 8 s |

复测时已经被后续提交修掉的：两个同名参考文件互相覆盖（上传名带内容指纹）、缺失的首帧文件通过校验、首帧锚定的默认行为。

## 真实 ComfyUI 0.37.2 上验证了什么

环境：`git clone --branch v0.37.2`、CPU 版 PyTorch、`requirements.txt` 原样（前端 1.52.7、模板包 0.11.69），加当天的 KJNodes、ResCascade、LBH 放大节点；模型目录里按真实文件名放空的占位文件。没有显卡，没有权重。

- **节点定义**：从 `/object_info` 读出全部 H3 节点和本流程用到的核心节点、三个节点包的节点——必填 / 可选、默认值、界面名。改正了节点表里 5 处（`MiniMaxH3ImageToVideo` 的 `vae` 是必填、`AddGuide` 的四个可选输入、`FunControlNetApply` 的 `model_patch` 和 `vae`、`MiniMaxH3SigmaShift` 在界面里叫 ModelSamplingMiniMaxH3、`CreateVideo` 的 fps 默认是 30）。
- **模板**：0.37.2 自带的模板包（0.11.69）里有全部 H3 视频模板和用到的出图模板，节点都在；它们和 GitHub 上最新的版本不完全一样（自带的 Qwen 2.1 文生图模板没有提示词扩写支路）。用真实前端把 13 个模板导出成 API 格式，读出实际生效的默认值：都是 0.4 MP、5 s、20 步不挂 LoRA，开关打开才是 Turbo。
- **脚本对真实服务器**：上传、排队、等待、取回视频和图片、相同任务跳过、批量、`/free`、日志都在真实服务器上走通（用一个不需要模型的工作流）。真实服务器暴露了模拟服务器测不出的三个问题：预检把模板里不再连着输出的节点和写成 `values.a` 的动态输入判成错误——原样导出的官方模板会被拦下；失败任务的报错是一大段带堆栈的 JSON；`--write-workflow` 写出的文件不带种子。都已修。
- **读懂官方模板**：脚本现在能顺着模板里的开关和分辨率选择器读出实际的步数、LoRA、画布，原样导出的模板可以直接用 `--set` 驱动。
- **附带的工作流**：11 个文件、15 种用法（草稿、20 步档、`--anchor`、Sage、精修、fl2va / i2va / t2va、文生图改尺寸和批量、1–3 张参考的编辑）全部被服务器的校验器接受，随后停在第一个加载器上（占位文件是空的）——这是预期的终点。

## 仍然没有验证的

采样本身。附带的工作流、`H3 Hires Fix` 二采、`--anchor`、Sage 节点、所有耗时和显存数字，都要在用户的 4090 上第一次跑时确认；`assets/first-run-checklist.md` 是为此排的顺序。
