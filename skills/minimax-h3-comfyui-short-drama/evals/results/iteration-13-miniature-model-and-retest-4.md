# 迭代 13：用微型模型把采样执行到底 + 装机与规划第四次复测（2026-11-23）

两件事。一是前三轮一直写着「没有采样过一帧」的那条线往前推了一大步：在没有显卡的机器上，用一套**微型的随机权重 H3** 把附带的工作流从文本编码一路执行到存片。二是第四次请一个没有上下文的 agent 复测，按它的发现改了一批脚本和文档。

## 一、微型模型：第一次把附带的工作流执行到底

### 做法

真实的 H3 底模 33B、文本编码器 32B，这台机器装不下也跑不动。但 ComfyUI 0.37.2 是从权重文件的张量形状推出模型结构的，所以可以造一套结构相同、宽度很小的替身：

| 部件 | 真实的 | 替身 |
|------|--------|------|
| DiT | 5376 宽、50 层 | ComfyUI 自己的 `MiniMaxH3Model` 类，256 宽、3 层；键名、`pruned` 的 8 维曲线基（`adaln_t_table`）、每层的 int8 + convrot 量化（用 comfy-kitchen 自己的量化函数）都和发布的文件一致；旋转位置编码的频率表和时间曲线表是用 Range 请求从真文件里取的那几十 KB |
| 文本编码器 | Qwen3-VL-32B，5120 宽、50 层 | 同一个类，256 宽、仍是 50 层（加载器靠第 50 层的键认它）。只改了 ComfyUI 配置表里的宽度数字，分词、参考图过视觉塔、token 标签、加载器的识别都是原代码 |
| LoRA | 208 / 259 个模块 | 同样的键名和布局，只含替身有的那几层 |
| 视频 VAE、音频 VAE、LBH 放大器 | — | **真实权重**（迭代 11 下载的） |

文件按真实文件名放进一台真实的 0.37.2，附带的 `*.api.json` 不改一个字，用 `comfy_submit.py` 照文档里的命令提交；只把画布缩到 448×256 / 320×192、时长缩短（CPU 上解码一帧要好几秒）。出来的画面是噪声——**验证的是整条接线在运行时成立，不是画质**。

|------|------|

| `--media` 接 5 张参考图 + 1 条音色（脸、全身、场景、道具） | 通过（73 帧） |
| 关掉 Turbo：20 步、不挂 LoRA（`--set 146.value=false`） | 通过 |
| `--anchor`：首帧钉在第 0 帧、第二镜关键帧钉在第 96 帧，整段 243 帧 | 通过（320×192、10.12 s） |
| 精修 `h3_ref2va_refine.api.json`：一采 → `H3 Hires Fix`（真实的 LBH 权重）→ 解码 | 通过：出 640×352；控制台 `[H3HiresFix] (16, 28) -> (22, 40), sigmas [0.45, 0.225, 0.0]` |
| 带首帧的 Ref2VA 段加 `--anchor` 再精修 | 通过；节点打印 `dropped 1 pass-1 keyframe(s)`——钉在第 0 帧的首帧是按一采尺寸编码的，二采时被去掉 |
| 分块精修 `h3_ref2va_refine_split.api.json`：124 帧 | 通过：LBH 放大（`temporal chunking: T=37 chunks=2`）→ `MMH3 Split Upscale` 分两块各 2 步 → 640×352、124 帧 |
| 草稿带 `--keep-latent` | 通过：take 文件夹里多出视频、音频两个 `.latent` |

| 从存下的 latent 接着精修（`h3_ref2va_refine.api.json --from-latent <那条 take 的文件夹>`） | 通过：一采不重跑，两个 `.latent` 传回、读入、拼回，二采出 640×352 |

| 首帧段的精修 `h3_fl2va_refine.api.json`（首尾帧段按 seed 重跑；首帧段用 `--from-latent`） | 都通过，出 640×352。节点打印 `[H3HiresFix] dropped 2 pass-1 keyframe(s) (start/end image) sized for pass 1`（首帧段是 `dropped 1`）——文档里「按一采尺寸编码的首尾帧会被自动去掉」是读源码得出的，现在跑出来了 |
| 首帧段的分块精修 `h3_fl2va_refine_split.api.json`：90 帧 | 通过：512×288、90 帧 |
| v1.2 布局的 LoRA（多 51 个时间调制层）挂在 `pruned` 底模上 | 任务跑完，控制台每个时间调制层一行 `ERROR lora diffusion_model.blocks.N.adaln_proj.linear.weight shape '[…, 8]' is invalid for input of size …`——预览里的 advice 事先说的就是这件事 |
| 同一个 LoRA 挂在不带 `pruned` 的底模上 | 通过，没有任何 `ERROR lora` |

### 顺带查清的

- **LoRA 挂没挂上的那行日志**：`Model MiniMaxH3 prepared for dynamic VRAM loading. … N patches attached.` 只在 DynamicVRAM 加载路径下打印（N 卡默认开；带 `--disable-dynamic-vram` / `--highvram` / `--gpu-only` / `--cpu` 启动时没有）。文档里原来只写「看有没有这一行」，现在写明了条件。
- **int8 底模挂 LoRA 的旧加载路径**（反量化 → 加 LoRA → 再量化）在替身上实际走通。4090 上默认走的是另一条（DynamicVRAM，LoRA 以补丁形式随权重装载），这条没有执行过。

### 仍然没有验证的

画面、口型、耗时、显存；Sage 的两个节点；DynamicVRAM 路径；真实权重下 int8 + LoRA 的数值表现。这些只能在 4090 上确认，顺序仍是 `assets/first-run-checklist.md`。

## 二、装机与规划第四次复测

测试 agent 没有上下文，只读 skill 的文档，按用户的条件（Windows 11、RTX 4090、ComfyUI 0.37.2、只能走 HuggingFace / GitHub、手里没有素材）把出图、30 s 分镜、批量草稿、选片对账、精修这几段重点走了一遍；能跑的命令都在真实的 0.37.2 上跑了（40 个任务被服务器接受，80 份日志）。

**结论**：第一批草稿「部分可以，偏向可以」；30 秒成片「部分可以」。前三次依次是「不行」「部分可以」「部分可以，接近可以」。

| 发现 | 性质 | 处理 |
|------|------|------|
| 按旧提示词抽的草稿能被悄悄采纳：上一段观测到的结尾和计划不一样之后，`[CHANGED]` 只在那一次构建打印，下一次就是 `[unchanged]`，`observe_take.py` 照收 | 脚本缺陷 | `observe_take.py` 采纳前对照片段旁边的 `run.json`：按旧提示词或旧参考抽的不收（看过接得上再加 `--stale-ok`）；`build_prompts.py` 每次都列出哪些成片是按旧提示词抽的 |
| `observe_take.py` 把 s01 的片段当成 s03 的收下 | 脚本缺陷 | 段不对、帧数不对的不收（`--force` 才收） |
| 前一段重新采纳了另一条、结尾变了，后面已采纳的段没有任何提示 | 脚本缺口 | 采纳时把「它是从上一段的哪个状态开场的」记进分镜；之后 `observe_take.py` 当场提示 `CHECK THE CUT`，`validate_episode.py` 每次都提醒，直到确认这一刀或重做 |
| 「从第一条采纳的片段里截音色样本」和「先批量抽完全部草稿」互相打架：样本一挂上，后面段的提示词变了，之前抽的草稿作废 | 文档矛盾 | 流程写明音色是批量的例外：先抽每个主角第一次开口的那一段，截样本，再批量；`build_prompts.py` 打印一行 `ORDER` 点名是哪几段 |
| 出图阶段要手写 17 个提示词文件，文件名、tag、九宫格的命令都得猜；没有脚本读 `sheet_phrase` 和 `first_frame_prompt` | 流程缺口 | 新脚本 `plan_stills.py`：从分镜写出全部出图提示词，逐张列出命令（工作流、三个图像输入各接谁、尺寸、候选数、存成什么），打印总张数。它给复测那份分镜（16 张图，含一张关键帧、一张两步首帧、一张背面视图）列出的命令和 agent 手工推出来的一致，逐条提交给真实服务器预检，全部通过 |
| 文档说 30 s 样片 44 张图，按 skill 自己的规则数出来是 54 张左右 | 错误陈述 | 改成以 `plan_stills.py` 打印的张数为准，并写明少算的是哪几样 |
| `i2va` 段（两张正脸的首帧规定用它）没有精修工作流、接不了音色参考 | 流程缺口 | 新增 `h3_fl2va*_refine*.api.json` 四份（真实服务器接受，并在微型模型上执行通过，见第一节）；文档写明 `i2va` 段的嗓音不受锚点约束、怎么处理，以及要锁音色的两人对白把首帧设计成过肩走 `ref2va` |
| 提示词路径忘写 `@`（把文件名当提示词发出去）、把尺寸写成 `2688x1536`（预检通过后服务器回 HTTP 400）、1920×1080 的首帧、1024×1000 的定妆照都显示 `preflight ok` | 脚本缺口 | 前两种拒绝并给出正确写法；出图尺寸不是本流程用的那几档、首帧图的比例和画布不一样时给 advice |
| Sage 草稿配了不带 Sage 的精修工作流按 `--seed` 重跑，没有提示（一采不是同一条） | 脚本缺口 | 每条 take 记下一采的设置；`--seed` 重跑时设置不一样就警告 |
| 预计时长只看同一个文件夹里的成片 | 文档与工具不符 | 没有时再看这一集其它段的成片 |
| 联络表的「末尾可用帧」在文档写的命令下落在定格里 | 文档与工具不符 | 给了 `--episode` 时默认跳过声明的 1 s 定格 |
| 四处互相矛盾：Sage 与 Low VRAM Attention 能不能同开；一张清楚的脸走 `ref2va` + 首帧还是 `i2va`；冒烟测试用 Ref2VA 跑纯文字而工具拒绝纯文字段用 Ref2VA；清单第 2、3 项要不要先 `--dry-run` | 文档矛盾 | 各统一成一种说法，并写明原因 |
| 「计时看第二条」的命令只出一条，重跑会被当成已完成跳过 | 错误陈述 | 命令加 `--batch 2`，并说明重测要换 seed |

它确认可用的：自检、连通测试、冒烟测试命令、预检；出图的三种工作流和各种接法；分镜校验 → 渲染 → 提示词 → lint；四批草稿的预览与确认；`--as-planned` 之后下一段 `[unchanged]`；尾帧接力；八条精修路线全部被服务器接受；`--from-latent` 的各种提示。skill 文件夹在测试前后哈希一致。

## 回归

## 执行用例一览

一共 18 条，17 条通过；没通过的一条是 Sage 版（缺 `sageattention` 包，见上表）。每条通过的标准：命令以 `done in …` 结束，取回的 mp4 尺寸、帧数、24 fps 都对，并且带一条等长的 32 kHz 立体声。顺带量到一个数：生产尺寸下（1344×768、10 s、5 张参考图、951 词的提示词）文本编码器输出 6,504 个 token，其中提示词 1,365、每张参考图约 1,030；同一次里 DiT 侧的 5 张参考图各是 1,008–1,024——「每张参考图合计约 2,000 个 token」有了实测。
