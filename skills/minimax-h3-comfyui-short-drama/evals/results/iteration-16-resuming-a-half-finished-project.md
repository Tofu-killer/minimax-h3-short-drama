# 迭代 16：接手一个做到一半的项目——第七次独立测试（2026-11-24）

前六次测试都是从零做起。这一次换了角度：用户重启了 App，之前那个 agent 的对话没了，什么交接都没有，只剩项目文件夹。测试 agent 拿到的只有 skill 和这个文件夹，用户只说一句「接着把这一集做完，给我成片」。

测试机和前两轮一样（真实的 ComfyUI 0.37.2 + 微型随机权重 H3，画面和声音都是噪声），验证的是流程和工具。

## 留给它的现场

我按 skill 写的做法亲手做出来的半成品，三段各 5 秒：

- 第一段有两条草稿，采纳了其中一条，**结尾和计划不一样**（`--deviation`）；
- 第二段的两条草稿和提示词都是按第一段**计划的**结尾做的，首帧也是——现在全都对不上了；
- 第三段是后来加进分镜的：首帧没做，提示词没出；
- 一个角色在第一段和第三段都开口，没有音色样本；
- 更早的时候还粗剪过一版：`selects/` 里放着两条草稿（其中一条不是后来采纳的那条），剪辑单、字幕、成片都是那一版的。

H3 任务上限 9 个。它用了 7 个（两段草稿各 2 条、三条精修），另有 1 个因为测试机自己的服务器中途被重启而丢失重排（不算数）。

## 结论

| 问 | 答 |
|----|----|
| 只凭 skill 能不能看懂做到一半的项目 | **部分能**。进度总览（`project_status.py`）说对了：哪条是采纳的、`selects/` 里放着错的片段、第二段的提示词过期、第三段缺图、要先截音色样本、成片不是最终的。没说的：第二段的首帧是按旧结尾做的、正在跑的任务、这个项目用的画布和许可设置、前后段接不接得上 |
| 能不能做完，不浪费任务、成片里没有错的或过期的片段 | **部分能**。这一次做到了（7 个任务没有一个白跑，成片逐段核对过）——但靠的是抓住了一条只打印一次的提示、并且自己去翻 `project.yaml`。照工具给的「下一步」命令原样执行，会多排一批任务，剪辑检查也会放过一条错的片段 |

它确认不用猜就能做的：进度总览的第一屏和音色那一块；`build_prompts.py` 的 `[CHANGED]` / `[unchanged]`；出图清单的 `MAKE AGAIN`；`observe_take.py` 的几种拒收；打断之后（退出码 130）和服务器重启之后的续取；从保留的 latent 精修（精修和草稿的声音相关系数 0.995）；先批量、后对账——第二段按计划采纳之后，第三段按计划抽的草稿仍然有效；剪辑单、字幕、混音、导出各自的过期提醒；`selfcheck.py` 55 项全过。

它要自己动手才知道的：第一段偏离计划的具体内容；第二段的首帧和第一镜动作写的还是计划里的姿势；画布 320×192、精修目标 448×256、项目要营利（都只在 `project.yaml` 和旧片段的 `run.json` 里）；第三段缺场景裁切和出图提示词；旧剪辑单为什么不带警告。下面的表就是照这两张清单改的。

## 它发现的问题和处理

代价最高的几条，都属于「对话丢了，工具又没把这件事留在盘上」：

| 发现 | 后果 | 处理 |
|------|------|------|
| 提交了、但结果还没取回的任务，重启之后谁都看不见：进度总览只认有 `run.json` 的片段，会让你「去出草稿」；而 `handle.json` 里没有当初的命令，照总览给的命令提交（设置略有不同）会把那个还在跑的任务的文件夹挤进 `_prev_`、再排一个新任务 | 一个任务白跑，后面再多排一个 | `comfy_submit.py --collect <片段文件夹>`：任务受理时就把片段的完整记录、当时的命令和日志行写进 `handle.json`，所以只凭文件夹就能取回结果（任务还在跑就等）。往里面有未取回任务的文件夹提交别的命令会被拦下。进度总览把这种任务列出来，并把取回作为这一段的下一步。在真实服务器上试过：取回的记录和正常跑完的只差一个耗时字段；测试进行中我用它在项目副本上取回了测试 agent 正在跑的那条精修 |
| 上一段按「和计划不同的结尾」采纳之后，下一段的首帧该不该重做，只在采纳那一刻和第一次重建提示词时各说一次——都说给了已经丢掉的对话。之后进度总览、出图清单、校验器都不提 | 草稿从一张和开场对不上的首帧出发 | 做成持久的检查：首帧比上一段采纳的片段还早、而那条片段的结尾偏离了计划——`project_status.py`、`plan_stills.py`（`CHECK`）、`build_prompts.py`、`validate_episode.py` 每次都说，直到把图重做，或者看过之后 `plan_stills.py --fits <首帧>` 确认。`observe_take.py` 现在记下采纳的时间 |
| 进度总览打印的出片命令是工作流的默认值：1344×768、不带 `--log`。这个项目是在别的画布上做的，画布只写在没有脚本读的 `project.yaml` 里 | 照抄命令就按错的尺寸出片（测试机上预计 228 分钟），片段也不进 takes 日志 | 命令沿用项目里已有片段的做法：最近一条草稿 / 精修用的工作流文件（带不带 Sage）和尺寸覆盖，并带 `--log logs/takes.csv`；草稿不是 1344×768 而又还没有精修过时，精修命令附上约 1.4 倍的目标尺寸 |
| 进度总览给的出图命令没有 `--t2i zimage`。营利项目照抄，定妆照 / 母版 / 道具的命令就悄悄换回研究许可的 Qwen-Image 2.1 | 许可问题 | `plan_stills.py` 把 `--t2i`、`--canvas`（新增：片子不在 1344×768 上做时首帧和关键帧的尺寸）、`--back` / `--side` 记在清单的记录里，之后不带参数也沿用，并打印一行说明；`--forget` 清掉 |
| 提示词、参考、seed 都和采纳的片段相同、但设置不同的片段（同 seed 关 Turbo 的 20 步重拍——文档自己的例子）被当成「采纳片段的精修」，进剪辑单没有任何警告 | 错的片段进成片，所有工具都不出声 | 这种片段现在算另一条片段：没有二采标记、一采设置又不同的，`make_edl.py` 和进度总览都警告 |
| 粗剪时还没采纳就做的剪辑单自己不带警告，`mix_episode.py` 只会复述剪辑单里存着的警告 | 「先粗剪、后采纳」留下一部没有任何警告的成片 | 剪辑单记下分镜的路径；`mix_episode.py`（`--dry-run` 也一样）在混音那一刻拿分镜现在记的采纳片段再对一遍，并指出哪几段还不在片子里 |
| 粗剪留在 `selects/` 里的草稿：进度总览说「都做完了」，`make_edl.py` 却每次都按文件名把它当候选推荐回来，不说它不是采纳的片段；`--overwrite` 会把它重新放进片子。文档还说成片能从 `selects/ + edit/` 重新装配，而总览给的命令是 `--pick` 直接指到 `takes/` | 错的片段随时可能回到片子里 | `make_edl.py` 说明每个没在用的文件是什么（不是采纳片段的让你拿走）；`--overwrite` 重建时，`--pick` 进来的条目按原来那个文件重建；进度总览列出没在用的文件；一段两个文件时点明哪个是采纳的并推荐它；文档改成两种放法都行 |

其余：

| 发现 | 处理 |
|------|------|
| 预览说「[resume] 会取回，不重新提交」，可服务器重启后早已不认识那个任务，实际会整个重跑 | 预览先问服务器，任务不在就写明要重新排一遍 |
| 提示词没出时报的路径是「分镜旁边」那个位置，而项目里别的首帧都在项目根目录下 | 报分镜里写的那个名字，并说明先在哪儿找、后在哪儿找 |
| 进度总览从「出草稿」直接跳到「选一条」，没提 QC | 「选一条」那一步列出 `qc_probe.py` / `qc_dialogue.py` / `contact_sheet.py` 的命令 |
| QC 用通配符扫整个段的文件夹，把过期的草稿也算进去，没有任何标记 | 五个 QC 脚本都多打一行，点名其中按旧提示词抽的片段 |
| `qc_dialogue.py` 每跑一次就把报告整个覆盖，只跑一段会冲掉别的段的结果 | 报告按片段累积 |
| 联络表写的「1 shot(s)」是检测到的镜头数，分镜里是 2 | 写成「found」，和分镜不一致时把分镜的数也写上 |
| `observe_take.py` 看片之后给的命令只有 `--write` 那种写法 | 两种都给（`--as-planned` 在前），并带上本次用过的 `--small-ok` |
| 一条精修、两条草稿拼成的片子，总览说「都不需要再做什么」 | 多一行 `sizes`：哪几段是哪种尺寸、小的会偏软 |
| 导出的工程是不是按现在的剪辑导的，没有地方说 | 导出时在 `edit/<集>.exports.json` 记下当时的剪辑，总览说明每份导出是否过期 |
| `--stale-ok` 采纳的片段，首帧后来被同名覆盖：用它自己留的 `media.json` 精修，仍然警告「参考变了」，并且又提示去用那份 `media.json` | 这种情况改用那条片段当时发给服务器的那一份（还在 ComfyUI 的 input 目录里，文件名带内容哈希）；找不到时警告里点名是哪个文件变了，不再绕回同一条提示 |
| 前一段后来又按另一种结尾重新采纳，后一段已采纳的片段和它接不上了：校验器会说，进度总览（接手时 SKILL.md 只让你看它）却说「都不需要再做什么」 | 进度总览把这种接缝列成 `cut !!`，并作为那一段的下一步 |
| 采纳的片段文件被同名替换：校验器警告，进度总览不提 | 总览标出 `THE FILE WAS REPLACED`，下一步是重新采纳 |
| 成片文件被别的文件顶替（比如换成一个 3 秒的文件），总览仍说「属于当前剪辑」——它只读报告 | 混音报告记下成片的哈希，对不上就说 |
| `.media.json` 里的参考路径是绝对路径：项目挪了位置、换了盘或换了机器之后，`build_prompts.py` 误判成「参考文件被换过」，照它说的命令去精修又报找不到文件 | 新出的提示词写相对项目根目录的路径；老的绝对路径失效时按路径的尾部在当前项目里找回来（`…/first/s03.png` → `first/s03.png`），诊断不再出错 |
| 字幕过期的警告只打印、没进混音报告；片子里有不是采纳片段的片段时，最后一行照样是 `OK` | 报告在最后才写，带上全部警告和「有几段不是采纳的片段」；这种片子的最后多一行说明：技术上没问题，但不是选定的那部片子 |
| （自己查出来的）提交时存进 `handle.json` 的命令带着那个批次的 `--confirm` | 存的时候去掉 |
| 上一段偏离计划之后，这一段第一镜的动作还是按计划写的：重建出来的提示词前半句说实拍的状态、后半句接着写计划里的动作，自相矛盾，lint 也放行。「回头读第一镜」同样只提醒一次 | `--deviation` 采纳时在分镜里记一条 `handover_note`（下一段首镜文字当时的指纹）；首镜一个字没改之前，校验器、`build_prompts.py`、进度总览每次都说，总览把它排在出提示词和出草稿之前 |
| 第一段偏离了什么，总览不说；画布、是否营利、草稿设置只在没有脚本读的 `project.yaml` 里 | 总览把偏差写在该段的标题行，把 `project.yaml` 里的这几项抄在最上面；`plan_stills.py` 发现它写着 `commercial: true` 而清单用的是研究许可的模型、或它记的画布和清单用的不一样时警告 |
| 成片里有不是采纳片段的片段时，`mix_episode.py` 的验收行照样是 `OK`、退出码 0 | 这种片子照样出，但退出码是 4，最后一行写明不是选定的那部片子；故意粗剪加 `--rough-cut` |
| 文档两处矛盾：出图一节一处说已有的提示词文件「不会被覆盖」，另一处说分镜改了会重写；精修一节的示例命令还是 `--seed`，SKILL.md 说默认 `--from-latent` | 都改成实际的行为：脚本写的提示词跟着分镜重写、手改过的不动；精修默认从保留的 latent 开始，没存才 `--seed` |

## 这一轮自己加的

- **配乐**：skill 以前只在文档里说配乐用什么模型，没有现成的工作流——做到成片的链路在这里有个缺口。现在附带 `acestep15_music.api.json`（ACE-Step 1.5 XL turbo，MIT；从 0.37.2 自带的官方模板经真实前端导出），歌词默认 `[Instrumental]`，时长只填一处，输出 flac；`models.json` 多一组 `music`（四个文件的大小和哈希在 HuggingFace 上逐个核对过），预览会列出时长 / BPM / 调 / 描述并拦下空描述，进度总览在剪辑齐了之后给出命令。真实的 0.37.2 接受了它；没有装过模型，没有出过声音。
- **混音之后再动声音**：加配乐、换配乐文件（同名）、调电平、字幕重新对时——以前的检查只看剪辑点和片段，成片会被当成最新的。现在混音报告记下声音部分的指纹和烧进去的字幕文件，变了就说；配乐比成片短也会在动手之前警告。
- **提示词文件里的参考路径改成相对项目根目录**：项目挪到别的盘或别的机器上照样能用，片段旁边留的那份也一样。
- **上游复查**（`docs/13-github-survey/14-index-triage-2026-11-23.md` 末尾）：官方模板库 11 月 23 日加了 MiniMax-H3-Image 的「换角色」模板（进了 `image-stage.md` 和 `image-prompts.md` §13；H3-Image 的许可全文读了一遍）；KJNodes 的 `MiniMax H3 Prompt Weight` 多了两个视频模式，但在真实的 0.37.2 上它一执行就报 `ImportError`（要 ≥ 0.45），SKILL.md 里照此改了；其余上游仓库没有新提交。
- 自检里一条早先的断言一直是恒真的（进程内调用时工作目录不对，所有文件都读成不存在），改成在项目根目录下执行。

## 测试机的一次事故

测试进行到一半，两台测试服务器因为后台任务到时被宿主停掉了两三分钟，测试 agent 正在跑的一条精修丢失。这不是 skill 的问题；但它顺带验证了一件事——`comfy_submit.py` 当时的说法（「服务器不再认识这个任务，原样重跑就会重新提交」）是对的，同时暴露了上表里预览那一条。

## 没有做的

- 真权重下的一切（画面、口型、耗时、显存）、Sage 的两个节点、DynamicVRAM 加载路径、Windows。
- 出图工作流和配乐工作流都只通过了服务器校验。
- H3-Image「换角色」需要 ComfyUI ≥ 0.45，没有在任何机器上跑过。

## 回归

`selfcheck.py` 56 项全过（多了一项「混音不只对剪辑点，还对配乐、电平、台词时间和烧进去的字幕」；其余新情形并进了已有的项目里：未取回的任务、总览沿用项目的画布、首帧和首镜的持久提醒、出图清单记住选择、同 seed 另一种设置的片段、混音时再对一遍分镜和退出码 4、配乐 / 字幕 / 成片文件变了之后混音过期、配乐预览、挪过位置的项目）；临时目录里的回归套件全过；真实 ComfyUI 0.37.2 上 29 种用法全部被服务器接受（多了配乐那一种）；在测试 agent 留下的成片项目副本上重放了它报告的每一种情形，新版本都给出了提示，而对它最终的成片不报任何误警。微型模型上用改过的提交脚本重跑了四种任务（两个系列各一条存 latent 的草稿、各一条从 latent 的精修），全部出片；另做了一次实弹演练：真实的 H3 任务跑到 30 秒时把提交脚本杀掉，再往同一个文件夹提交别的命令被拦下（`[pending] NOT queued`），`--collect` 只凭文件夹等到任务跑完，取回成片和两个 latent，记录完整，takes 日志里正好一行。
