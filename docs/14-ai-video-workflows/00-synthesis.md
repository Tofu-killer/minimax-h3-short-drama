# 00 · 跨方向综合：现有 AI 视频工作流教会我们什么

> 2026-11-21。汇总本目录五份报告（01 开源模型 × ComfyUI、02 端到端流水线与 agent、03 商业模型与创作者工作流、04 配音 / 口型 / 后期、05 一致性与分镜生图），回答三件事：行业的通用做法是什么、每类镜头该交给谁、我们的 skill 因此改了什么。
> **验证口径**：五份报告是文献与源码调研，没有在用户的 RTX 4090 上跑任何模型，也没有调用任何云端模型；速度、显存、价格都是作者或官方标价。本轮**实测过的**只有 skill 的新脚本（在一支 38 s 的真实 H3 成片上，Linux + ffmpeg 6.1 + CPU）和 ComfyUI 各发布 tag 的源码核对。每条结论后面标的状态：`实测` = 本轮亲手跑过；`已核源码`；`文献` = 只有别人的数据。

## 1. 七句话结论

1. **方法已经收敛**：资产先行 → 静帧当控制层 → 以「一次生成」为单位的分段分镜 → 参考生视频（带原生声音）→ 逐段审片 → 时间线混音 → 成片 + 可编辑工程。闭源平台、开源制片台、agent skill 套件走的是同一条骨架（02、03）。
2. **H3 本身在第一梯队**，云端的 H3 Max / Pika H3 Flex 等是它的后训练衍生（03）。所以「走出 H3」不是换更好的模型，而是只在它的结构性短板上换工具：> 15 s 不能切的单镜、全身接触的打戏、指定轨迹的运镜、给定音频的精确口型、成片局部修补。
3. **决策前移到静帧**是成本最大的杠杆：改一张分镜图与改一段视频的成本差一个量级（03 的实测单价是 3 积分对 55 积分）。本地同理——首帧 20 步几十秒，视频一段几分钟。
4. **一致性的主流做法换代了**：身份适配器（PuLID / InstantID 等）的官方仓库基本停更，2026 年的做法是「一张锚点图 + 编辑模型逐张派生 + 冻结与过期标记」（05）。
5. **声音是分层做的**：对白 / 非人声 / 环境声底 / 拟音 / 配乐各走各的轨，台词文本锁定、时间来自对齐，时间线混音后再定响度（04）。
6. **QC 要落成脚本，并且对照原始剧本**，不是对照 AI 自己扩写的提示词（02）。开源里仍然没有一个系统把「本地抽卡 → 自动评分 → 自动返工」完整跑通——这是所有人共同的缺口，不是我们独有的。
7. **本地开源视频是「三主一辅」**：Wan 2.2 家族（Apache-2.0，无声，开源线停在 2.2）、LTX-2.3 / 2.5（原生音画，单次 20 s）、MiniMax H3，辅以 HunyuanVideo 1.5（01）。ComfyUI 0.46 核心已原生支持其中绝大多数。

**过程中发现并改掉的四个问题**（都来自实测，不是文献）

1. 把台词原文当提示喂给 whisper-small 会让它「听到」没说过的句子 → 质检与对时一律不给提示，改用拼音比对。
2. ffmpeg 的 scene 阈值分不开「同一房间的硬切」（0.19–0.28）和「画面里飞舞的纸」（0.30）→ 改用前后 4 帧均值的台阶 + 邻域比 + 持续性。
3. 按整段平均响度对齐电平，会把只有一句短台词的段连同环境声一起抬 9 dB → 改成按台词区间量响度，并限制音效峰值被限幅的量。
4. sidechain 压缩在真实对白上只压得动配乐约 3–6 dB，而且片段里的音效也会触发 → 改成按台词时间画增益包络。另外 `alimiter` 默认有 5 ms 延迟（两级就是 10 ms 音画偏移），已用 `latency` 补偿。

**独立可用性测试**

脚本写完后，请一个没有任何上下文的 agent 只凭 skill 文档，对真实片段完成「质检 → 成片 → 导出工程」。它交付了成片，同时报回 27 条摩擦点，其中 9 条是脚本缺陷：剪映草稿导出在特定帧数下崩溃、烧录字幕偏一帧、定格尾的检查口径与剪辑单不一致导致漏检、字幕普遍早出 0.4–1.2 s、片段里已有的字幕没人发现又被叠了一层、手改的字幕时间会被覆盖、联络表缺最后一帧、切点定位偏 2 帧、把「峰值偏高」当成削波。全部已修并复测；记录在 `skills/…/evals/results/iteration-4-post-chain-usability.md`。这一步的教训是：自己写的测试只覆盖自己想到的用法，换一个只读文档的使用者才看得到说明与行为对不上的地方。

**第二次独立可用性测试（创作链路）与官方原文复核**

换一个没有上下文的 agent 走「剧本 → 分镜 → 提示词 → 提交预览 → 接上一段实拍末态」，再把脚本出的提示词逐条对着官方指南和 ComfyUI 源码核一遍。改掉的要点（全表见 skill 的 `evals/results/iteration-5-authoring-chain-usability.md`）：

- 两处**写错的事实**：音色参考的保留标记应是音频专用的 `reference`（不是 `attribute_transfer`）；API 工作流里的参考输入是带点的扁平键 `ref_images.ref_image_0`（不是嵌套对象，写错不报错、参考被静默丢掉）。
- 提示词构建器按官方完整示例重写：字段名独立成行、一条定义一行、`[Shot 1]` 之前只有一句风格；人不用名字；首次清楚出场处带外貌、之后切镜带短提醒；台词后闭嘴；音色参考每句引用。
- 人物描述拆成两用：进视频提示词的短外貌（`identity_phrase`）与只给生图用的完整外貌（`sheet_phrase`）。
- `comfy_submit.py --media` 把提示词、帧数和参考接线从 `.media.json` 写进工作流，预检对账「提示词提到的」与「实际接上的」参考。
- 本地节点对提示词没有长度上限（文本编码器是 Qwen3-VL-32B，直接读原文）；7000 字符只是云端 API 的限制。

**第三次独立可用性测试（创作链路复测）**

构建器重写之后换一段新剧本、换一个 agent 再走一遍。它排出的三个最贵的问题都改了（全表见 `evals/results/iteration-6-authoring-chain-retest.md`）：

- 段间交接：状态里提到的人下一段没绑定就会在选片之后才报错 → 状态可以提到本集任何资产，没绑定的用文字称呼。
- 状态用的是上一个机位的画面坐标、结束状态被写进特写镜头 → 状态改写人在房间里的位置；结束状态只在末镜拍得到全屋时进提示词。
- 分镜规则散在四份文档里、数字互相不同 → `storyboard-and-assets.md` §1 定为唯一口径。

另外：`comfy_submit.py` 的预览会提示工作流里没接 VAE、步数与 LoRA 不配、画布比例与画幅不一致；流程表里的命令现在照抄就能跑。
